# CPU 求值测量

这组测量用于检查默认低质量效果的 CPU 开销。它测量 Blender 依赖图求值，也就是更新驱动、几何节点和形态键所需的时间；不包含视口绘制、着色器渲染、透明叠加或合成，因此不能换算成实际帧率。

2026-10-22，Blender 5.2.2，Linux x86_64 / glibc 2.41，环境可见 3 个逻辑 CPU。每种情况创建 8 个实例，先运行 3 帧，再记录 30 帧。全部使用 Low，粒子每实例 64 个，Cloth 每实例保存 25 个姿态。

| 效果（各 8 个实例） | 求值顶点 | 面数 | 中位数 | P95 |
| --- | ---: | ---: | ---: | ---: |
| 冲击波 | 512 | 256 | 0.82 ms | 0.94 ms |
| 弧形刀光 | 528 | 256 | 1.87 ms | 2.00 ms |
| 粒子爆发 | 6,144 | 10,240 | 3.36 ms | 3.55 ms |
| 已烘焙 Cloth | 648 | 512 | 0.97 ms | 1.03 ms |
| 冲击波 + 粒子的组合 | 6,656 | 10,496 | 5.34 ms | 6.56 ms |

P95 表示约 95% 的采样帧不超过这个时间。面数统计网格多边形，环和布面主要是四边形，粒子为三角形；不能只按此列比较渲染开销。组合中的每个实例包含一个冲击波和一个粒子爆发，所以共有 16 个效果层。

8 个 Low Cloth 的 1–25 帧烘焙合计 0.34 秒。该数值包含本机求解和形态键写入，不代表其他硬件或更复杂输入。保存后的播放不重新求解 Cloth。

这些结果支持保留当前默认数量，尚不足以承诺集成显卡上的渲染流畅度。透明效果铺满屏幕、提高粒子细分或增加合成辉光，都可能产生这里未测量的主要开销。实际项目应先减少粒子 Count、效果数量和画面覆盖，再考虑提高质量。

2026-10-23 在相同 Blender 版本、3 个逻辑 CPU 的 Linux 环境另测 8 个 Low 连续发射器：默认 Rate=64、Lifetime=0.6、Emission Seconds=1.5、Duration=48，仍先运行 3 帧再记录 30 帧。
求值中位数为 5.33 ms，P95 为 7.08 ms；创建合计 0.23 秒。第 9 帧每实例有 23 个粒子，8 个实例共 2208 个顶点、3680 个三角面；数量随填充和尾段变化，不是固定负载。
此结果同样不包含绘制和渲染。控制连续发射开销时，减少 Rate 或 Lifetime；最多 2048 个存活槽只是安全上限，不代表低配置设备适合使用这个数量。

复测命令：

```sh
blender -b --factory-startup --python-exit-code 1 --python tools/benchmark.py
blender -b --factory-startup --python-exit-code 1 --python tools/benchmark.py -- --instances 16 --frames 60
```

脚本要求新的后台进程和未保存的默认场景，会清空该测试进程中的场景来逐项测量，不应拿生产文件运行。详细结果写入忽略的 `work/benchmark.json`。不同机器和后台负载会改变数值，应使用同一环境比较后续改动。
